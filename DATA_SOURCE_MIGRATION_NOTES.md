# Data Source Migration Notes

The loan service now reads from the modern normalized schema (`borrowers`, `loan_products`,
`loan_accounts`, `payments`). The legacy CDW tables are still loaded at startup only as the
source for the migration. The REST contract is unchanged.

## Runtime layout

- One in-memory H2 database (`jdbc:h2:mem:loandb`) holds both schemas during the transition.
  `spring.sql.init.schema-locations` loads `schema-legacy.sql` and `schema-modern.sql`, and
  `data-legacy.sql` seeds the legacy tables only.
- `schema-modern.sql` is a copy of `data/modern-schema/modern_tables.sql`. H2 2.x accepts the
  `BIGINT PRIMARY KEY AUTO_INCREMENT` columns as written, so no `GENERATED BY DEFAULT AS IDENTITY`
  rewrite was needed.
- On startup `MigrationRunner` (an `ApplicationRunner`, toggled by
  `loanservice.migration.enabled`) runs `DataMigrationService.migrate()` and then
  `MigrationReconciliationService.reconcile()`. If reconciliation fails, startup fails.
- `LoanService` reads only from the modern repositories. The `Legacy*` entities and
  repositories are marked `@Deprecated` and are used only by the `migration` package.

A single datasource was chosen over two datasources because both schemas live in the same
in-memory database for this workshop. That avoids a second `EntityManagerFactory` and
transaction manager.

## Decisions

### Surrogate keys and public identifiers
- Every modern table uses a `BIGINT` identity primary key (`@GeneratedValue(strategy = IDENTITY)`).
- The legacy natural keys stay as unique business keys: `borrowers.external_id` (BORR_ID),
  `loan_products.code` (PROD_CD) and `loan_accounts.account_number` (LN_ACCT_NBR).
- API path variables keep their old meaning. `/api/loans/{id}` and `/api/loans/{loanId}/payments`
  take an account number, and `/api/borrowers/{id}` takes an external id. `LoanService` turns each
  one into a surrogate key with `findByAccountNumber` / `findByExternalId`, then follows FKs
  (`findByBorrowerIdOrderByIdAsc`, `findByLoanAccountIdOrderByPaymentDateDesc`).
- **Schema addition:** `payments.external_id VARCHAR(20) UNIQUE` stores the legacy
  `PMT_SEQ_NBR`. column_mappings.md allows this ("legacy ID stored if needed"). It is needed
  because the API exposes `paymentId` (for example `PMT-2025120001`), and it is also the
  duplicate-detection key for payments. The column was added to both
  `data/modern-schema/modern_tables.sql` and `schema-modern.sql`.

### FK resolution order
Tables are migrated in dependency order:
1. `borrowers`
2. `loan_products`
3. `loan_accounts`: `borrower_id` is looked up from `borrowers.external_id = BORR_ID`, and
   `product_id` from `loan_products.code = PROD_CD`
4. `payments`: `loan_account_id` is looked up from `loan_accounts.account_number = LN_ACCT_NBR`

A row whose FK does not resolve is rejected and reported, not inserted.

Legacy rows are read in their natural (insertion) order, so surrogate ids follow the legacy
row order. List endpoints sort by `id`, so `/api/loans` and `/api/borrowers` return rows in
the same order as before.

### Type conversion (migration only)
`LegacyValueParser` and `LegacyRecordMapper` follow column_mappings.md:
- `MM/DD/YYYY` becomes `LocalDate`, or `LocalDateTime` at 00:00 for `created_at` / `updated_at`.
  Strict resolution means an impossible date such as `02/30/2020` is rejected.
- Amounts have their commas removed and become `BigDecimal`. Plain decimals and integers are
  parsed after trimming.
- Direct-copy columns are copied unchanged.

The service layer no longer parses strings. `parseLegacyAmount`, `parseLegacyDecimal` and
`parseLegacyInteger` were removed.

### Status/code expansion
Code tables live in `com.workshop.loanservice.domain`. Each entry carries its legacy code, its
stored modern value and its API label:

| Column | Legacy → stored value | API label (unchanged) |
|---|---|---|
| borrowers.status | ACT→ACTIVE, INA→INACTIVE | (not exposed) |
| loan_products.is_active | ACT→true, INA→false | (not exposed) |
| loan_accounts.status | ACT→ACTIVE, CLO→CLOSED, DFT→DEFAULT, FRB→FORBEARANCE | Active, Closed, Default, Forbearance |
| loan_accounts.property_type | SFR→Single Family, CND→Condominium, MFR→Multi-Family, TWN→Townhouse | Single Family Residence, Condominium, Multi-Family Residence, Townhouse |
| payments.type | REG→REGULAR, EXT→EXTRA, PRT→PARTIAL, PRE→PREPAYMENT | Regular, Extra, Partial, Prepayment |
| payments.status | PST→POSTED, REV→REVERSED, NSF→NSF, PND→PENDING | Posted, Reversed, Non-Sufficient Funds, Pending |

- The stored values come from column_mappings.md. For property type, the mapping lists only
  SFR and CND and says "etc." for the rest. MFR → `Multi-Family` and TWN → `Townhouse` follow
  the same pattern. The seed data has no MFR rows.
- The modern stored values (`ACTIVE`, `Single Family`) differ from the labels the API has always
  returned (`Active`, `Single Family Residence`). To keep the contract, `LoanService` maps stored
  value to label with `CodedValue.labelFor`. This is a lookup only, with no parsing. As in the
  legacy API, an unrecognised value is returned as-is and a missing value becomes `Unknown`.

### Denormalization removal
- `CDW_LN_ACCT.BORR_FST_NM`, `BORR_LST_NM` and `BORR_SSN_LST4` are not migrated. A loan's
  borrower name now comes from the `borrower_id` FK. The migration logs a warning if the legacy
  denormalized name differs from the borrower master record. No row in the seed data differs.
- `CDW_BORR_MSTR.BORR_REC_TYP` is not migrated.

### Edge cases
- Null or blank strings become `NULL` for typed and code columns.
- If a value is malformed, or a NOT NULL column (`first_name`, `original_amount`, `payment_date`,
  `type`, ...) is missing, that row is **rejected**. It is logged with the legacy key and the
  column name, and the other rows carry on. A rejection shows up as a reconciliation count
  mismatch, so startup fails instead of serving partial data.
- An unknown status, type or property code is copied unchanged with a warning, matching the old
  pass-through behaviour. An unknown `PROD_STAT_CD` is rejected because it cannot become a boolean.
- Duplicates: a row is skipped if its key (`external_id` / `code` / `account_number` / payment
  `external_id`) already exists. This makes the migration idempotent and safe to re-run.
- Database errors (constraint violations and similar) roll back the whole migration transaction.

## Validation

`MigrationReconciliationService` checks the following and logs a summary at startup:
- Row counts, legacy vs modern: 5 borrowers, 5 loan_products, 5 loan_accounts, 10 payments.
- Column totals for every amount column, compared numerically after conversion.
- Per loan account: borrower and product FKs point to the legacy BORR_ID and PROD_CD, and the
  original amount, balance, monthly payment and rate all match.
- Per payment: the loan FK and the total amount match.

Tests:
- `ApiGoldenFileTest` covers all five endpoints, 17 requests in total. It compares the responses
  with golden JSON in `src/test/resources/golden/`, which was captured from the legacy-backed
  service before `LoanService` was rewired.
- `DataMigrationServiceTest` checks counts, FKs, typed values, idempotent re-runs and
  reconciliation.
- `LegacyRecordMapperTest` and `LegacyValueParserTest` cover the mapping rules and edge cases.

### Intentional API differences
1. **`originalAmount` scale.** `loan_accounts.original_amount` is `DECIMAL(12,2)`. Legacy values
   with no decimals (`"285,000"`) used to serialize as `285000` and now serialize as `285000.00`.
   The numbers are identical. This affects `/api/loans`, `/api/loans/{id}` and the `loans` array
   in `/api/borrowers/{id}`. Every other amount in the seed data already had the column's scale,
   so its output is byte-identical. The golden test removes only this `.00` suffix before
   comparing.

There are no other differences. Dates are still returned as `MM/dd/yyyy` strings, field names
and order are unchanged, and the payment list, the borrower list and every other field are
byte-for-byte identical.

Behaviour differences that the seed data does not trigger:
- Payments are now ordered by a real `DATE`. The legacy code sorted `MM/DD/YYYY` strings, which
  gave the wrong order across years.
- A blank legacy code used to be echoed back as `""`. It is now stored as NULL and reported as
  `Unknown`.

## Follow-ups
- Remove `schema-legacy.sql`, `data-legacy.sql`, the `Legacy*` classes and the `migration`
  package once the modern tables are seeded directly.
- Optional: move `property_*` out of `loan_accounts` into a `properties` table if several loans
  can share a property or appraisal history is needed. It is left as is for the current model of
  one property per loan.
